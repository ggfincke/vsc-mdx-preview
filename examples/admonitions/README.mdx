# Admonition Directive Syntax

MDX Preview supports Docusaurus/Starlight-style admonition directives using the `:::` syntax. This feature works in **both Safe Mode and Trusted Mode** without requiring any imports.

---

## Basic Admonitions

### Note

Use notes for general information and context:

:::note
This is a note admonition. Notes are great for providing additional context or background information that helps readers understand the topic better.
:::

### Tip

Use tips for helpful suggestions and best practices:

:::tip
This is a tip admonition. Tips share useful advice, shortcuts, or best practices that can improve the reader's workflow.
:::

### Info

Use info for informational content:

:::info
This is an info admonition. Similar to notes, but typically used for more specific informational content.
:::

### Warning

Use warnings for potential issues:

:::warning
This is a warning admonition. Warnings alert readers about potential problems, gotchas, or things to watch out for.
:::

### Danger

Use danger for critical warnings:

:::danger
This is a danger admonition. Danger callouts are for critical warnings about breaking changes, security issues, or actions that could cause data loss.
:::

### Caution

Use caution for proceed-with-care situations:

:::caution
This is a caution admonition. Caution is similar to warning but often used for situations where the reader should proceed carefully.
:::

### Important

Use important for key information:

:::important
This is an important admonition. Important callouts highlight critical information that shouldn't be overlooked.
:::

## Multi-Paragraph Content

Admonitions properly handle multiple paragraphs:

:::note[Extended Note]
This is the first paragraph of the admonition. It introduces the topic we're discussing.

This is the second paragraph. It provides additional details and context about the topic.

This is the third paragraph. Blank lines between paragraphs are preserved, maintaining proper formatting.

And you can have as many paragraphs as needed to fully explain your point.
:::

## Nested Admonitions

You can nest admonitions by using more colons for the inner ones:

:::note[Outer Note]
This is the outer admonition content.

::::warning[Inner Warning]
This is a nested warning inside the note!

Nested admonitions can be useful for highlighting important information within a larger context.
::::

Back to the outer note content.
:::

## Comparison: Directives vs GitHub Alerts

MDX Preview supports two callout syntaxes. Here's how they compare:

### Directive Syntax (:::)

:::tip[Directive Syntax]
This uses the `:::type` syntax from Docusaurus/Starlight.

- Supports custom titles via `[Title]`
- Works in both Safe and Trusted Mode
- More flexible styling
:::

### GitHub Alert Syntax (> [!TYPE])

> [!TIP]
> This uses GitHub's blockquote-based alert syntax.
>
> - Standard across GitHub-flavored Markdown
> - Limited to 5 types: NOTE, TIP, IMPORTANT, WARNING, CAUTION
> - Title is the type name

### Side-by-Side Examples

:::

**GitHub alert syntax:**

Both syntaxes are supported and will render similarly!

### Troubleshooting

:::caution[Common Issue: Port Already in Use]
If you see an error like `EADDRINUSE: address already in use :::3000`:

1. Find the process using the port:
   ```bash
   lsof -i :3000
   ```

2. Kill the process:
   ```bash
   kill -9 <PID>
   ```

3. Or use a different port:
   ```bash
   PORT=3001 npm run dev
   ```

## Long Content

:::note[Comprehensive Guide to Error Handling]
Error handling is a critical aspect of building robust applications. This guide covers best practices for handling errors in JavaScript and TypeScript applications.

## Types of Errors

There are several categories of errors you'll encounter:

1. **Syntax Errors** - These occur when the code doesn't follow the language's grammar rules.

2. **Runtime Errors** - These happen during program execution, such as:
   - `TypeError` - Wrong type used
   - `ReferenceError` - Undefined variable accessed
   - `RangeError` - Value out of range

3. **Logic Errors** - The code runs but produces incorrect results.

## Best Practices

### Use Try-Catch Blocks

```javascript
async function fetchData(url) {
  try {
    const response = await fetch(url);
    if (!response.ok) {
      throw new Error(`HTTP error! status: ${response.status}`);
    }
    return await response.json();
  } catch (error) {
    console.error('Fetch failed:', error.message);
    throw error; // Re-throw for calling code to handle
  }
}
```

### Create Custom Error Classes

```javascript
class ValidationError extends Error {
  constructor(field, message) {
    super(message);
    this.name = 'ValidationError';
    this.field = field;
  }
}

// Usage
throw new ValidationError('email', 'Invalid email format');
```

### Handle Errors at Boundaries

- Catch errors at API boundaries
- Log errors with sufficient context
- Provide meaningful error messages to users
- Never expose stack traces in production

## Error Monitoring

Consider using error monitoring services like:

- Sentry
- Bugsnag
- LogRocket

These tools help you track and debug errors in production.
