# Admonition Directive Syntax

MDX Preview supports Docusaurus/Starlight-style admonition directives using the `:::` syntax. This feature works in **both Safe Mode and Trusted Mode** without requiring any imports.

---

## Standard Admonitions

### Note

Use notes for general information and context:

:::note
This is a note admonition. Notes are great for providing additional context or background information that helps readers understand the topic better.
:::

### Tip

Use tips for helpful suggestions and best practices:

:::tip
This is a tip admonition. Tips share useful advice, shortcuts, or best practices that can improve the reader's workflow.
:::

### Info

Use info for informational content:

:::info
This is an info admonition. Similar to notes, but typically used for more specific informational content.
:::

### Warning

Use warnings for potential issues:

:::warning
This is a warning admonition. Warnings alert readers about potential problems, gotchas, or things to watch out for.
:::

### Danger

Use danger for critical warnings:

:::danger
This is a danger admonition. Danger callouts are for critical warnings about breaking changes, security issues, or actions that could cause data loss.
:::

### Caution

Use caution for proceed-with-care situations:

:::caution
This is a caution admonition. Caution is similar to warning but often used for situations where the reader should proceed carefully.
:::

### Important

Use important for key information:

:::important
This is an important admonition. Important callouts highlight critical information that shouldn't be overlooked.
:::

## Extended Admonition Types (Crossnote)

These additional types follow the crossnote/Material Design conventions used by Markdown Preview Enhanced and similar tools.

### Summary

Use summary for abstracts and TL;DR sections:

:::summary
This is a summary admonition. Great for executive summaries, abstracts, or TL;DR sections at the top of a document.
:::

### Hint

Use hint for subtle suggestions:

:::hint
This is a hint admonition. Hints are softer than tips — useful for nudging the reader toward a solution without being prescriptive.
:::

### Success

Use success for confirming positive outcomes:

:::success
This is a success admonition. Use it to confirm that a step completed correctly or that a configuration is valid.
:::

### Question

Use question for FAQs and open questions:

:::question
This is a question admonition. Perfect for FAQ sections, design questions, or prompting the reader to think about something.
:::

### Failure

Use failure for known issues and broken states:

:::failure
This is a failure admonition. Highlights known failure modes, broken configurations, or things that won't work as expected.
:::

### Bug

Use bug for known bugs and defects:

:::bug
This is a bug admonition. Document known bugs, unexpected behavior, or issues that are being tracked for a fix.
:::

### Example

Use example for code examples and demonstrations:

:::example
This is an example admonition. Wrap worked examples, sample configurations, or demonstration code in this type for visual distinction.
:::

### Quote

Use quote for citations and attributions:

:::quote
"The best way to predict the future is to invent it."
— Alan Kay
:::

### Todo

Use todo for work-in-progress items:

:::todo
This section is incomplete. Add documentation for the new authentication flow before the v3.0 release.
:::

### Attention

Use attention for things that need focus:

:::attention
This is an attention admonition. Similar to warning, but emphasizes that the reader should pay close attention to what follows.
:::

## Alias Types

Several aliases map to canonical types:

:::abstract
`:::abstract` is an alias for `:::summary`. Both render the same cyan style.
:::

:::tldr
`:::tldr` is also an alias for `:::summary`.
:::

:::check
`:::check` is an alias for `:::success`. So are `:::done`.
:::

:::help
`:::help` is an alias for `:::question`. So is `:::faq`.
:::

:::fail
`:::fail` is an alias for `:::failure`. So is `:::missing`.
:::

:::snippet
`:::snippet` is an alias for `:::example`.
:::

:::cite
`:::cite` is an alias for `:::quote`.
:::

Override the default title using `[Title]` syntax after the type:

This note has a custom title "Getting Started" instead of just "Note".
:::

:::warning[Migration Required]
**Version 3.0 introduces breaking changes.**

The following APIs have changed:

1. **Authentication** - The `auth.login()` method now requires an options object:

   ```javascript
   // Before (v2)
   auth.login(username, password);

   // After (v3)
   auth.login({ username, password, remember: true });
   ```

2. **Data fetching** - The response format has changed:

   | Property | v2 | v3 |
   |----------|----|----|
   | Data | `response.data` | `response.result.data` |
   | Status | `response.status` | `response.meta.status` |

3. **Configuration** - New required fields:

   - `apiVersion` (string, required)
   - `timeout` (number, optional, default: 5000)

See the [migration guide](#) for detailed instructions.

## Multi-Paragraph Content

Admonitions properly handle multiple paragraphs:

:::note[Extended Note]
This is the first paragraph of the admonition. It introduces the topic we're discussing.

This is the second paragraph. It provides additional details and context about the topic.

This is the third paragraph. Blank lines between paragraphs are preserved, maintaining proper formatting.

And you can have as many paragraphs as needed to fully explain your point.
:::

## Nested Admonitions

You can nest admonitions by using more colons for the inner ones:

:::note[Outer Note]
This is the outer admonition content.

::::warning[Inner Warning]
This is a nested warning inside the note!

Nested admonitions can be useful for highlighting important information within a larger context.
::::

Back to the outer note content.
:::

## Comparison: Directives vs GitHub Alerts

MDX Preview supports two callout syntaxes. Here's how they compare:

### Directive Syntax (:::)

:::tip[Directive Syntax]
This uses the `:::type` syntax from Docusaurus/Starlight.

- Supports custom titles via `[Title]`
- Works in both Safe and Trusted Mode
- 17 types + 12 aliases for comprehensive callout coverage
- Material Design elevation styling
:::

### GitHub Alert Syntax (> [!TYPE])

> [!TIP]
> This uses GitHub's blockquote-based alert syntax.
>
> - Standard across GitHub-flavored Markdown
> - Limited to 5 types: NOTE, TIP, IMPORTANT, WARNING, CAUTION
> - Title is the type name

### Side-by-Side Examples

**Directive syntax:**

:::note
This is a note using directive syntax.
:::

**GitHub alert syntax:**

> [!NOTE]
> This is a note using GitHub alert syntax.

Both syntaxes are supported and will render with Material Design elevation!

### API Documentation

:::warning[Rate Limiting]
The API enforces the following rate limits:

- **Free tier**: 100 requests/hour
- **Pro tier**: 1,000 requests/hour
- **Enterprise**: Unlimited

Exceeding these limits will result in a `429 Too Many Requests` response.
:::

:::danger[Authentication Required]
All API endpoints require authentication. Requests without valid credentials will return a `401 Unauthorized` error.

**Never expose your API key in client-side code!**

```javascript
// WRONG - key exposed in browser
fetch('/api/data', {
  headers: { 'X-API-Key': 'sk_live_abc123' } // DON'T DO THIS!
});

// CORRECT - key used server-side only
// Use environment variables and server-side code
```
:::

### Troubleshooting

:::caution[Common Issue: Port Already in Use]
If you see an error like `EADDRINUSE: address already in use :::3000`:

1. Find the process using the port:
   ```bash
   lsof -i :3000
   ```

2. Kill the process:
   ```bash
   kill -9 <PID>
   ```

3. Or use a different port:
   ```bash
   PORT=3001 npm run dev
   ```
:::
